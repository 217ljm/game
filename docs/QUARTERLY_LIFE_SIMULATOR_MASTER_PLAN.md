## 0. 文档权威、交接方式与旧方案处置

### 0.1 本文档解决什么问题

项目此前先后尝试了网页式文字档案、背景图加行动卡、仪表盘式季度草案、固定舞台与热点互动。它们都没有准确落实项目真正需要的产品形态，相关方向文档已从正式文档目录删除。

本文档将产品重新冻结为：

> **一款以季度为回合、以角色一生为主线、以生活模块和具体行动为主要操作、以即时游戏反馈和长期因果为体验核心的中文竖屏人生模拟游戏。**

玩家不是在场景里找热点、移动角色或猜下一步，也不是在网页里填写季度表单。玩家要持续看见自己的角色、年龄、身份、资源和近期人生，在生活模块中选择具体行动；行动加入后保留在本季度安排中，并立即产生人物、资源、动画和声音反馈，再由确定性 Core 让这些选择在几年、几十年后改变可进入的人生。

### 0.2 与旧文档冲突时的优先级

发生冲突时按以下顺序执行：

1. **产品形态、玩法、页面、UI、美术与实施顺序：以本文档为准。**
2. 确定性核心、分层依赖和渐进迁移：继续遵循 [`TECHNICAL_ARCHITECTURE.md`](TECHNICAL_ARCHITECTURE.md)。
3. 季度资源、三个月内部执行和点击量：继续复用 [`QUARTERLY_TURN_SYSTEM.md`](QUARTERLY_TURN_SYSTEM.md) 中不与本文冲突的规则。
4. 六项终身属性、短期状态、兴趣、习惯和社会事实：以本文第 6～7 节、当前模拟实现和专项系统文档为准。
5. 一生不是固定成功路线：继续遵循 [`LIFE_MAINLINE_SYSTEM.md`](LIFE_MAINLINE_SYSTEM.md)。
6. 历史、职业、收入、住房、家庭和教育现实：继续读取各阶段系统文档及 `data/calibration/`。

### 0.3 已删除的错误方向

轻场景、角色移动、地图、热点寻找、DOM SceneRuntime、旧 MVP、旧年度回合、旧网页 UI 重构和强制盲测方案已从正式文档目录删除，不再作为历史参考被新任务引用。

`public/light-scene/`、`public/spikes/light-scene/` 及相关旧代码暂时只保留为代码归档，避免误删验证证据；它们不得进入正式数据加载、正式路由、正式构建、正式检查或新增开发。需要彻底清理代码时另开一次精确删除任务。

### 0.4 新对话的执行原则

新对话开始后应先完整阅读本文档、技术架构和 [`PROJECT_DEVELOPMENT_STATUS.md`](PROJECT_DEVELOPMENT_STATUS.md)，再检查工作区和相关实现。不得仅凭 README 中的旧进度描述启动开发。所有阶段状态、当前项目说明、文件所有权、实施记录、检查结果、风险和下一步只更新 `PROJECT_DEVELOPMENT_STATUS.md`，不得新建第二份进度文档。

## 1. 产品定义

### 1.1 游戏主题

玩家从改革开放初期出生，在家庭、城乡、教育、职业、关系、婚育、住房、财富、健康和时代变化中度过一生。

游戏主线不是考大学、发财、结婚、买房或把属性加满，而是：

> **在真实社会条件与个人选择共同作用下，通过具体生活逐渐成为一个具体的人。**

### 1.2 目标体验

玩家在游玩中应持续感受到：

1. 我清楚现在是哪一年、几岁、第几季度，正在过怎样的生活；
2. 我能在当前年龄做不止一种事，而不是每次只有一个假选择；
3. 时间、精力和金钱会限制我，但不会替我决定人生；
4. 每次行动都有立即反馈，不需要等到长报告才知道发生了什么；
5. 早年的玩耍、启蒙、关系和习惯会影响后来的兴趣、能力与机会；
6. 收入稳定性、家庭负担和教育机会来自具体事实，不是系统主观贴标签；
7. 同一时代、同一出身也能因为长期行为形成明显不同的人生；
8. 结局能说明“我是怎样一步步成为这个人”，也能回看没有选择的道路。

### 1.3 产品形态

- 中文竖屏单机人生模拟游戏；
- 390×844 为首要设计视口；
- 主要操作是进入生活模块、执行行动、处理事件、推进季度；
- 主界面是 Phaser/Canvas 2D 游戏屏幕，不是网页信息门户、仪表盘或表单；
- 角色形象、年龄、身份、资源、近期人生记录和当前季度安排持续可见；
- 学校、活动、关系、家庭、生活/资产等模块使用游戏菜单和行动面板；
- 人物头像/立绘、图标、状态条、转场、结果动画和声音承担即时反馈；
- 记录页允许高文字密度，主玩法页不允许长篇文字堆砌；
- 浏览器与 TapTap H5 只是运行容器；正式主玩法不继续扩大 `public/index.html`、`public/app.mjs`、`public/styles.css`；
- 开发与自测使用 Chrome，主发布策略仍以单独的发布文档和届时官方政策为准。

### 1.4 非目标

- 不做大型地图、开放世界、角色自由移动或寻路；
- 不做“场景中有人喊你，但玩家不知道为什么”的冒险叙事；
- 不做隐藏物品搜索、热点发现或点击背景猜交互；
- 不把背景图片、PPT 式切图或文章卡片当作完整玩法；
- 不逐日安排吃饭、睡觉、上厕所等常规行为；
- 不把每个季度拆成十几次机械确认；
- 不做唯一总分、完美人生或单一成功路线；
- MVP 不引入账号、排行榜、支付、广告和联网后端；
- 不迁移 Unity、Godot、Three.js 或 3D 引擎；2D 正式表现层按本文采用 Phaser/Canvas。

## 3. 人生主线与章节结构

### 3.1 唯一主线

“人生本身”是主线。系统不预设玩家必须成为哪种人，而是持续回答三个问题：

- **眼下要维持什么：** 健康、学习、工作、住处、现金和责任；
- **正在积累什么：** 能力、技能、兴趣、习惯、关系和社会经验；
- **想要靠近什么：** 从长期行为中显现的生活方向。

### 3.2 七个人生章节

| 年龄 | 章节 | 核心问题 |
| --- | --- | --- |
| 0～5 岁 | 认识世界 | 我在怎样的生活中长大，又反复靠近什么？ |
| 6～11 岁 | 家庭与学校 | 在学习、家庭、朋友和玩耍之间，我正在形成什么？ |
| 12～17 岁 | 开始选择方向 | 成年正在靠近，我把时间和本事带向哪里？ |
| 18～24 岁 | 进入社会 | 我怎样获得自己的生活入口？ |
| 25～39 岁 | 建立自己的生活 | 工作、住处、关系和愿望如何共存？ |
| 40～59 岁 | 守住与改变 | 责任增加以后，我守住什么，又改变什么？ |
| 60 岁以后 | 后来的日子 | 离开全职工作后，我怎样生活，又留下什么？ |

### 3.3 六种动态人生方向

- 理解与求知；
- 动手与实践；
- 表达与创造；
- 关系与共同生活；
- 身体与生活节律；
- 工作与生活保障。

方向由真实季度行动、兴趣时数、人物经历和长期选择计算。它不是出生性格、职业锁定或成功评分，可以增强、改变、停滞或被放下。

## 4. 核心游戏循环

### 4.1 单季度循环

```text
进入季度
→ 看清年龄、身份、固定责任、时间、精力与金钱
→ 在游戏主屏查看本季可用生活模块
→ 打开模块并直接选择具体行动
→ 行动以令牌/图标/明确条目留在本季安排中
→ 每项行动立即产生输入、资源、人物和短演出反馈
→ 可能出现一件随机或关键事件
→ 玩家作出态度或取舍
→ 月内模拟完成三个月实际执行
→ 查看简短季度结果
→ 进入下一季度
→ Q4 后年度回望并年龄 +1
```

### 4.2 玩家真正操作什么

玩家的基本动词是：

- 查看；
- 进入模块；
- 选择行动；
- 选择投入方式；
- 与人物互动；
- 接受、拒绝、协商或延后；
- 休息；
- 调整本季安排；
- 处理事件；
- 推进季度。

“阅读长篇结果”不是基本动词，“移动角色找到热点”也不是基本动词。

### 4.3 连续行动与季度提交

为了同时保证游戏感和确定性，界面与核心分为两层：

1. 玩家点选行动后，游戏立刻把行动加入可见的本季度安排，预留时间、精力和金钱，并播放角色/人物/资源短反馈；行动不能选中后消失；
2. 玩家可以继续切换模块、调整强度或撤销尚未提交的安排；无需先点“加入本季”再点“完成选择”；
3. 屏幕只保留一个明确的“结束本季度/进入下一季度”动作，触发后由应用层提交稳定的 `quarter.plan` 命令；
4. Core 按三个月确定性执行计划、事件中断和实际完成度；
5. 已提交季度不能靠返回按钮重新抽取结果。

界面不得把“已安排”伪装成“属性已经增长”。属性、关系和兴趣的最终变化以 Core 结算为准；操作层可以立即显示人物动作、资源占用和倾向提示。

一次性事件行动可以使用独立 `event.choose` 或未来的 `action.perform` 命令，但同样必须由 Core 先产生事实，再播放表现。

### 4.4 年度循环

- Q1～Q4 逐季生活；
- Q4 结束后形成年度账本、重大变化和未走道路；
- 年度页只突出 3～5 个有意义的变化；
- 四季度详情默认折叠，可进入记录页展开；
- 年龄只在年度结算完成后增加一岁；
- 进入新年龄后，身份、责任、模块和行动池重新生成。

## 5. 时间、回合、精力与点击量

### 5.1 时间结构

- 1 年 = 4 个季度；
- 1 季度 ≈ 13 周；
- 1 季度内部模拟 3 个月；
- 12 个生活时间格表示三个月内可稳定安排的生活空间，不表示角色只生活了 12 小时；
- 固定责任先占时间，剩余格才由玩家安排；
- 上学、工作、睡眠、通勤和照护必须显示具体来源，不使用“负担中等”等人工等级。

### 5.2 固定责任

固定责任由实际状态生成，例如：

- 幼儿的睡眠、进食、清洁和被照护；
- 学生的上课、作业和通学；
- 就业者的工作日、班次和通勤；
- 父母、子女、病人和老人照护；
- 住房、家庭劳动和必要办事。

主界面显示“本季必须花时间的事情”，展开后看到来源和占用，不显示笼统评分。

### 5.3 终身体能与季度精力

- `fitness` 体能：0～100 的终身核心属性；
- `quarterEnergy` 精力：每季度重算的行动资源，建议 4～16；
- `timeSlots` 时间：每季度重新分配的容量；
- 三者字段、图标和文案必须分离。

基础季度精力为 10，由健康、心情、作息、疾病、伤势、工作、通勤和照护修正。体能主要影响运动、劳动、远行的消耗、恢复、成功率和伤害风险。

### 5.4 行动强度

| 强度 | 时间格 | 典型精力 | 含义 |
| --- | ---: | ---: | --- |
| 尝试 | 1 | 1～2 | 接触一次、体验或完成一次小事 |
| 定期 | 2～3 | 3～4 | 在季度内形成规律投入 |
| 重点 | 4～5 | 5～7 | 作为本季度主要生活方向 |

不是所有行动都提供三档强度。对话、看病、考试、搬家、表白等离散行动使用固定成本和具体选项；锻炼、学习、陪伴、兼职、兴趣练习等持续行动才使用投入强度。

### 5.5 休息与透支

- 主动休息占用时间但恢复精力、降低疲劳和压力；
- 未分配时间自动成为普通生活、临时玩耍、发呆和基础恢复；
- 最多允许透支 3 点精力；
- 透支提高疲劳、失败、疾病和受伤风险；
- 连续透支会形成持续疲劳并锁定高强度行动；
- 游戏不能鼓励玩家把每个时间格和精力点全部榨干作为唯一最优解。

### 5.6 不同年龄的操作量

| 年龄 | 玩家主动季度 | 单季典型行动数 | 普通年份基础交互 |
| --- | --- | ---: | ---: |
| 0 岁 | 自动记录 | 0 | 年度确认 1 次 |
| 1 岁 | Q3 | 1 个眼前反应 | 2 次 |
| 2 岁 | Q1、Q3 | 1 个自主尝试 | 3 次 |
| 3～5 岁 | Q1、Q3 | 1～3 项 | 3 次 |
| 6～11 岁 | Q1、Q3；关键季度可打断 | 2～3 项 | 3～5 次 |
| 12～59 岁 | Q1～Q4 | 2～4 项 | 5～7 次 |
| 60 岁以后 | Q1、Q3；安排可连续两季 | 2～3 项 | 3～5 次 |

关键事件可额外增加 1～2 次选择，但普通季度不应要求十几次确认。

### 5.7 自动延续

从同年第二个主动季度起提供：

- 延续上季度安排；
- 维持到年底，除非发生关键事件；
- 只在计划不可执行时提醒我；
- 普通季度快速结算。

自动推进仍保存完整季度事实，不能跳过模拟。计划因年龄、身份、金钱、时间、健康或人物条件失效时必须停下并说明原因，不能偷偷替换行动。

## 6. 人物属性、状态与成长

### 6.1 六项终身属性

| ID | 名称 | 含义 |
| --- | --- | --- |
| `health` | 健康 | 疾病、伤势、营养、睡眠和身体完整状态 |
| `fitness` | 体能 | 力量、耐力、灵活、协调和恢复 |
| `intelligence` | 智力 | 理解、记忆、逻辑、专注和创造能力 |
| `appearance` | 外表 | 五官、体态、气色、整洁和穿着形成的印象 |
| `social` | 社交 | 表达、共情、观察和处理人际关系的能力 |
| `willpower` | 意志 | 自律、韧性、自信和承受压力的能力 |

所有属性一生使用同一套 0～100 标尺，不随年龄重新校准，也不展示“同龄优秀”等易误解标签。

普通足月且无严重疾病的新生儿健康应明显高于半值；体能、智力、社交和意志按尚未发育的绝对能力保持较低。出生值与后续变化必须由具体出生事实和行为解释。

### 6.2 短期状态

- 心情；
- 压力；
- 疲劳；
- 本季度精力；
- 疾病与伤势；
- 临时自信、睡眠和营养问题。

短期状态可以明显波动，但不能伪装成终身能力。

### 6.3 成长方式

普通行动先积累不可见或半可见的成长经验/残差，不应每次点击都让核心属性 `+1`。

```text
成长经验 = 行动基础经验
         × 实际完成度
         × 投入强度
         × 连续性
         × 环境条件
         × 当前状态
         × 潜力效率
         × 边际递减
```

达到阈值后核心属性增长 1 点。界面要能说明这 1 点来自哪些季度的长期积累。健康可因疾病、伤势、治疗和恢复直接变化。

### 6.4 兴趣、技能与习惯

兴趣阶段：

`尚未接触 → 有过接触 → 兴趣萌芽 → 稳定兴趣 → 长期爱好`

兴趣来自具体行动的实际投入，不能在出生时随机贴标签。技能来自实践，不能由智力直接替代。习惯来自跨季度重复，例如作息、阅读、锻炼、储蓄、整洁、拖延、冒险、逃避和主动交往。

早期启蒙的主要作用是增加接触机会和后续行动概率，不是一次选择决定终身职业。

## 7. 社会现实与历史边界

### 7.1 只保存事实，不保存主观等级

禁止把以下内容作为核心状态：

- 教育资源：普通；
- 家庭负担：中等；
- 收入稳定性：偏低；
- 社会地位：一般。

应该保存：

- 所在地区、学校类型、班级规模、是否中断教育、通学距离；
- 家庭成员、职业、实际收入、失业月份、合同、工时和照护时间；
- 住房面积、产权、租金/贷款、迁居记录；
- 角色具体岗位、行业、单位性质、工资月份、换岗和晋升记录；
- 家庭现金、储蓄、债务和实际支出；
- 人物之间的具体事件和共同经历。

“稳定性”和“压力”等摘要只允许由这些事实派生并可展开解释。

### 7.2 历史与玩法分层

- `data/calibration/`：有来源、口径、年份和不确定性的历史观测；
- `data/gameplay/`：虚构人物、事件、行动和叙事；
- rules：公式、阈值、冷却和状态变化；
- 2026 年以后的内容必须标识为玩法情景，不冒充已观测历史；
- 历史观测、模型假设、推断和纯玩法内容必须在数据中保持可区分。

### 7.3 社会条件的作用

社会条件影响机会成本、可用行动、成功概率和风险，但不能直接写死“贫穷必失败”“城市必成功”。同样的个人属性在不同家庭、地区、年代和关系网络中，应面对不同选择和代价。

## 8. 生活模块与分龄行动池

### 8.1 模块是游戏菜单，不是网页页面

模块是 `LifeScreen` 内持续可见的游戏入口。点击后使用 Phaser/Canvas 行动面板、浮层或专门事件屏展示可执行行动，不跳转到层层返回的网站页面，也不打开需要滚动阅读的大抽屉。

每个年龄阶段最多显示 4～6 个核心模块，模块随身份动态替换。

### 8.2 分龄模块

| 年龄/身份 | 主要模块 |
| --- | --- |
| 0～2 岁 | 眼前、探索、亲人；大部分生活由家庭自动安排 |
| 3～5 岁 | 启蒙、玩耍、亲人、生活、身体 |
| 6～11 岁 | 学校、活动、关系、家庭、生活 |
| 12～17 岁 | 学业、兴趣、关系、家庭、生活/兼职准备 |
| 18～24 岁在校 | 学业、发展、关系、生活、资产 |
| 18～24 岁就业 | 工作、技能、关系、生活、资产 |
| 25～39 岁 | 工作、家庭、关系、生活、资产 |
| 40～59 岁 | 工作、家庭/照护、关系、健康、资产 |
| 60 岁以后 | 生活、健康、家庭、关系、资产/传承 |

模块只在实际成立时出现。例如没有工资和财产的幼儿不显示资产管理；没有子女时不显示育儿入口。

### 8.3 行动候选生成

候选必须读取：

- 年龄、年份、季度、人生阶段；
- 教育、工作、家庭和住房状态；
- 地区、季节、时代和可到达地点；
- 时间、精力、现金和健康；
- 属性、兴趣、技能和习惯；
- 人物关系、近期行为、事件、冷却和重复惩罚；
- 过去未完成的约定和长期主线。

候选生成后在本季度内固定。“换一批”只翻阅确定列表，不重新抽取结果。

### 8.4 行动在界面上的最低信息

默认行动项只显示：

- 图标、名称和行动对象；
- 时间、精力和金钱成本；
- 2～4 个潜在影响图标；
- 风险或前置条件；
- 是否可持续到下季度。

详细说明按需展开为次级信息。点击后，行动必须以视觉上稳定的令牌、图标或条目留在本季度安排中，并显示对象与成本；不得在首屏一次展开十几张长文字卡。

### 8.5 行动类型

1. **持续投入：** 学习、锻炼、练习兴趣、陪伴、兼职、储蓄；
2. **离散行动：** 看病、申请、考试、购买、搬家、表白、求职；
3. **人物互动：** 询问、聊天、共同活动、帮助、请求、拒绝、兑现约定；
4. **责任行动：** 作业、工作、照护、家庭任务；
5. **恢复行动：** 休息、散步、娱乐、减少负担；
6. **关键选择：** 升学、职业、婚育、住房、迁移、退休和重大健康决定。

### 8.6 可复用互动模板

首批只需建立六种高复用模板：

1. 学习练习：投入、顺序、重复、接受帮助；
2. 对话回应：态度、问题、承诺、拒绝；
3. 同伴活动：加入、观察、改变规则、退出；
4. 家庭协作：接受任务、询问边界、完成或延期；
5. 兴趣探索：观察、比较、制作、记录；
6. 身体活动：投入、休息、继续或停止。

不是每次行动都要做小游戏。互动模板的目标是让行动具备对象、过程、回应和选择，而不是把一段说明换成四段说明。

### 8.7 每项行动的完整数据

每项正式行动至少包含：

- 稳定 ID；
- 所属模块和类型；
- 年龄、时代、身份和状态条件；
- 行动对象/人物/地点；
- 时间、精力、现金和物品成本；
- 可选投入方式；
- 三个月过程或离散执行点；
- 短动作/姿态和人物回应 cue；
- 可能影响的状态、兴趣、技能、习惯、关系和长期事实；
- 中断、失败、受限和资源不足路径；
- 冷却、重复衰减和后续解锁；
- 一句短日记；
- 历史/玩法来源标记。

## 9. 人物关系系统

### 9.1 关系不是单一数值

关系至少由以下事实组成：

- 熟悉度；
- 信任；
- 亲近；
- 冲突/芥蒂；
- 最近联系时间；
- 共同经历；
- 未兑现约定；
- 当前处境、地点和可互动状态。

### 9.2 关系界面

人物卡默认显示：

- 头像/剪影、姓名、年龄和身份；
- 与玩家的关系；
- 最近一次共同经历；
- 当前情绪或处境；
- 1～3 项当前可发起互动；
- 为什么某些互动不可用。

人物详情不是档案文章。重要互动应进入短互动层，玩家可以陪伴、询问、共同活动、请求帮助、帮助对方、拒绝、延后或兑现约定。

### 9.3 跨年人物

玩伴、同学、老师、亲属、同事、邻居和伴侣必须能够跨季度、跨年份保留。关系变化要能追溯到共同生活，而不是仅靠赠礼按钮刷取。

## 10. 随机事件、关键事件与未走道路

### 10.1 随机事件

- 每季度至多发生一件普通随机生活事件；
- 候选读取年龄、年代、身份、家庭、教育、工作、关系和本季行动；
- 事件 RNG 与 UI 点击顺序分离；
- 同一种子、同一命令序列必须得到同一事件；
- 事件可在确定月份打断剩余计划；
- 已完成行动不能倒扣；
- 事件可改变剩余时间、精力、完成度、疲劳、压力、兴趣、关系和现金。

事件表现：

```text
状态或人物变化
→ 一句短提示/对白
→ 2～3 个态度或取舍
→ 短结果演出
→ 返回本季度
```

不得先给玩家一篇长文章，再要求从三篇长文章中选一篇。

### 10.2 关键人生事件

升学、离校、第一份工作、失业、迁移、伴侣、孩子、住房、照护、重大疾病、退休和死亡使用独立流程层。它们可以比普通行动包含更多信息，但必须明确：

- 当前事实；
- 可选道路；
- 每条道路的条件、所得与代价；
- 哪些结果是未知风险；
- 选择后立即发生的变化；
- 未来可能产生的长期影响。

### 10.3 未走道路

每次关键选择保存未选项和当时不可达项。年表与结局可以回看“当时还可能怎样生活”，但不能泄露未经玩家选择的全部未来随机结果。

## 11. 页面、信息架构与 390×844 布局

### 11.1 屏幕与模块的区别

游戏只保留少量真正的顶层屏幕；学校、活动、工作等是本季度生活模块，不是网站导航页面。

顶层屏幕：

1. 标题/继续游戏；
2. 新人生/出生；
3. **人生主屏（主要游玩时间）**；
4. 角色成长；
5. 关系网络；
6. 资产与家庭账本；
7. 人生记录/年表；
8. 结局/人生回望；
9. 设置；
10. 仅开发构建可见的调试台。

### 11.2 人生主屏

冻结的 390×844 游戏屏幕结构：

```text
┌─────────────────────────┐
│ 1984 · 6岁 · Q2  身份   │  年龄/季度持续可见
├─────────────────────────┤
│ 角色头像/半身像            │
│ 当前状态 · 人生方向 · 回应 │  角色不是装饰头像
├─────────────────────────┤
│ 时间 5/12  精力 7/10  钱 │  资源与责任
├─────────────────────────┤
│ 最近的人生                │
│ 行动/事件/人物反馈短记录   │  不是长文章
├─────────────────────────┤
│ [学校][活动][关系]         │
│ [家庭][生活/资产]          │  游戏模块
├─────────────────────────┤
│ 本季度安排                │
│ [练名字][和同伴玩][休息]  │  选中后持续可见
├─────────────────────────┤
│       结束本季度            │  唯一主动作
└─────────────────────────┘
```

原则：

- 首屏不滚动就能看到角色、状态、资源、生活模块、已选行动和唯一推进按钮；
- 行动选择使用游戏面板或浮层，可展开详情但不强迫阅读；
- 本季轨道最多直显 3～4 个行动，更多内容横向分页或折叠；
- 最近发生只显示 1～3 条短句；
- 详细三个月过程进入季度回望或记录页；
- 角色和行动反馈不能被底部 CTA、Toast 或导航遮挡；
- 不以无限纵向滚动、通用卡片栅格或大幅背景图替代游戏构图。

### 11.3 角色页

显示角色年龄形象、身份、六项属性、短期状态、兴趣、技能、习惯、当前生活方向，以及每项最近变化的真实原因。数值是辅助信息，不能把页面做成属性表格仓库。

### 11.4 关系页

以人物头像、最近共同经历和可发起互动为主，关系数值与计算解释为次级详情。

### 11.5 资产页

儿童阶段显示家庭环境与可理解的零用钱/物品；成年后显示现金、收入、支出、储蓄、债务、住房、物品和家庭责任。账本必须来自真实交易和月份，不使用财富等级替代。

### 11.6 记录页

记录页是唯一允许高文字密度的主要页面：

- 年度概览；
- 四季度明细；
- 重大事件；
- 收入、支出、职业和住房依据；
- 兴趣成长历史；
- 关系变化；
- 未走道路；
- 计算解释；
- 同期历史背景。

默认按自然年折叠，详细季度可展开。

## 12. UI、美术、动画与声音

### 12.1 视觉方向

采用“现代明快的移动端人生模拟游戏 + 克制的时代生活元素”。画面首先要读成游戏屏幕和角色人生，而不是移动网页、后台面板或 PPT。

- 主色：清爽蓝绿、珊瑚橙或明亮青色；
- 状态色：健康绿、精力黄、压力橙、风险红、关系紫；
- 年代感来自服装、家具、票据、建筑、交通和事件插图；
- 背景保持浅色、层次清楚和足够对比；
- 面板、标签、框体和按钮形成统一的游戏 UI 材质，不使用通用网页卡片库拼屏；
- 图标、头像、资源条和生活轨道承担主要视觉信息；
- 文字负责解释，不负责填满屏幕。

#### 12.1.1 字体与阅读密度规范

正式游戏只允许一套正文无衬线字体族和一套经批准的品牌/章节标题字体族。具体字体文件在许可、中文字符覆盖、包体与真机渲染验证完成后冻结；冻结前继续使用统一开发期回退栈，但 `Scene`、组件和业务内容不得自行写入 `Arial`、`Georgia`、`STKaiti`、`KaiTi`、`Microsoft YaHei` 等局部字体栈。所有 Phaser 文本必须通过统一文本 token/工厂创建，禁止继续在场景中散落字号、字重和字体族。

390×844 逻辑视口采用以下最低层级：

| 用途 | 建议字号 | 字重 | 阅读约束 |
| --- | ---: | --- | --- |
| 品牌/章节标题 | 24～28px | 600 或专用标题字 | 只用于极短标题，不承载正文 |
| 页面/弹窗标题 | 18～20px | 600 | 一屏同级标题不重复堆叠 |
| 卡片标题/主要按钮 | 15～17px | 500～600 | 必须先于说明文字被看见 |
| 正文/事件叙述 | 14～16px | 400 | 默认行距 6～8px；长段落必须分段或渐进呈现 |
| 辅助说明 | 12～13px | 400～500 | 只承载短句，不得成为主要阅读内容 |
| 极短元数据 | 11～12px | 400～500 | 仅限年份、标签、计数等非关键短信息 |

- 禁止用 10～11px 显示完整句子、行动结果、按钮、资源状态或事件正文；
- 正文默认常规字重，粗体只用于标题、关键数值、结果变化和主操作；禁止把 12～13px 全部设为粗体；
- 所有可能换行的文字必须显式设置最大宽度、对齐和行距，不以缩小字号解决溢出；
- 同一屏优先保留标题、正文、辅助说明三级层级，避免多种近似字号造成视觉噪声；
- 字体加载完成前不得进入正式可交互画面；加载失败必须使用度量接近的统一回退字体，不能让布局因平台字体变化而漂移；
- 可读性验收必须在 Chrome 390×844 真机流程中进行，至少检查主屏、行动卡、事件弹窗、季度结算、资产/记录长文本；自动截图只能证明未溢出，不能替代产品负责人的阅读疲劳判断。

#### 12.1.2 图标与视觉符号规范

正式 UI 禁止使用系统 Emoji 或文本符号承担模块导航、资源状态、按钮前缀、返回/关闭、趋势、事件类别和老物件缩略图。Emoji 的颜色、体积和风格随操作系统变化，不能作为发布级视觉资产；`▶`、`←`、`✕`、`▲` 等字符也不得冒充正式图标。Emoji 仅可作为开发期 `runtime-input` 占位，或在确有叙事需要且通过视觉验收的角色对白中出现。

- 全局功能图标采用同一套矢量家族。当前项目已有 Phosphor 图标依赖，正式 Phaser/Canvas 链路优先从中筛选并导出经过许可核验的本地 SVG/纹理图集，不在 Canvas 中直接依赖 DOM 图标字体；
- 图标数据只保存稳定语义键，例如 `module.learning`、`resource.cash`、`action.call`、`event.milestone`；业务数据、标题和按钮字符串不得内嵌可见 glyph；
- `asset-manifest` 必须增加 `ui` 图标类别及稳定 `AssetKey`/`iconKey` 映射。缺图时回退为统一几何占位并记录告警，不回退成 Emoji；
- 功能图标使用 24×24 基准网格、统一线宽、圆角与双色规则；颜色来自状态 token，不在单个事件里自由指定。常态、选中、禁用、警告必须靠形状/容器/文字共同表达，不能只靠颜色；
- 推荐显示尺寸：资源/HUD 16～20px，模块与行动 24～28px，事件类别 28～32px；可点击容器仍不得小于 44×44px；
- 年代老物件、纪念品和人物头像属于内容插画，不得用通用功能图标或系统 Emoji 代替。老物件使用 48～64px 的统一小插画/剪影规格，并通过稳定资产键加载；
- 同一语义只允许一个主图标，同一图标不得同时代表多个无关资源；图标旁保留短文字标签，不能要求玩家仅凭图形猜测；
- 19～24 岁及后续事件内容交付必须同时给出语义 `iconKey` 建议。共享图标注册表、素材 manifest 和全局样式由唯一所有者修改，内容子代理不得各自创建图标体系。

当前 `life-scene.ts` 中的 Emoji、局部字体栈和小字号粗体均视为待迁移灰盒，不因事件数量增加而转为正式标准。迁移顺序固定为：顶部 HUD 与五大生活模块 → 主操作与返回/关闭 → 事件类别与结果状态 → 年代老物件内容插画；每批迁移后运行 UI/浏览器检查并在 390×844 截图中核对字号、行距、基线、清晰度和跨平台一致性。

### 12.2 美术资产层级

P1/P2 就必须生产能反复复用的最小实机资产，不能把美术、动画和声音全部推迟到后期：

- 角色年龄头像/半身形象；
- 家庭、学校、邻里等氛围背景或事件底图；
- 家庭成员、同伴、老师等人物头像；
- 生活模块图标；
- 时间、精力、金钱、健康、兴趣、关系等状态图标；
- 6 种互动模板所需的姿态/表情；
- 关键事件插图；
- 季度轨道、年度推进和属性反馈特效；
- UI 音效与少量时代环境声。

背景与事件图负责交代年代、处境和人物关系，不承担可走区域、碰撞和热点。主屏不需要自由移动场景，但必须有持续角色、游戏面板、状态变化和转场。

### 12.3 最低动画语言

| 动画 | 建议时长 | 目的 |
| --- | ---: | --- |
| 游戏屏幕/行动面板进入 | 180～280ms | 建立层级 |
| 行动按下 | 100～160ms | 确认输入 |
| 行动进入季度安排 | 240～400ms | 表明已安排且不会消失 |
| 时间/精力扣除 | 220～450ms | 显示成本 |
| 人物姿态/表情变化 | 250～600ms | 显示当下回应 |
| 关系线/兴趣进度 | 300～550ms | 显示成长 |
| 随机事件聚焦 | 300～500ms | 打断普通节奏 |
| 月份推进 | 280～480ms | 显示时间流动 |
| 季度推进 | 450～700ms | 完成回合 |
| 年度/年龄推进 | 600～900ms | 形成阶段感 |

所有动画必须流畅、可跳过，不能决定结果。支持 `prefers-reduced-motion` 和游戏内“完整/减少/关闭”选项。动画失败、素材 404 或刷新后必须直接显示已经保存的事实。

### 12.4 行动四层反馈

每项行动至少提供：

1. **操作反馈：** 按压、选中、资源预留、进入并留在季度安排；
2. **过程反馈：** 角色动作、头像表情、人物回应、月份变化；
3. **即时反馈：** 一句结果、心情/疲劳/现金/关系变化；
4. **长期反馈：** 兴趣、技能、习惯、属性残差、未来解锁和事件种子。

### 12.5 声音和震动

- 模块切换、行动确认、资源不足、事件出现、季度推进使用短 UI 音效；
- 学校、家庭、街道、工作地点可使用极轻环境声；
- 关键节点才使用明显提示音；
- 声音默认可独立关闭；
- 震动只用于少量关键确认并可关闭；
- 声音和震动不参与任何模拟判断。

## 13. 首个正式垂直切片：1984 年 6 岁完整四季度

### 13.1 为什么选择 6 岁

6 岁同时具备学习、玩耍、家庭、同伴、兴趣、健康和入学变化，能验证玩家自身视角、行动丰富度、长期成长和现实条件，不需要先实现复杂工作、婚育与资产系统。

### 13.2 切片边界

首切片必须覆盖：

- 1984 年 6 岁 Q1～Q4；
- Q4 结束后进入 7 岁；
- 完整的主生活屏；
- 学校/启蒙、活动、关系、家庭/生活四至五个模块；
- 至少 16 项符合年龄的行动，其中每季度至少 8 项可用候选；
- 每季度可组合 2～3 项行动；
- 至少 3 名持续人物：一名照看者、一名同伴、一名老师或准老师；
- 至少 6 件条件化随机事件；
- 至少 2 条资源不足/条件受限路径；
- 至少 4 条跨季度因果；
- 兴趣萌芽、学校适应、同伴关系、家庭参与、健康节律和认知积累；
- 季度结果、年度回望、存档重载和 7 岁行动池切换。

不包含：

- 自由移动；
- 场景热点；
- 大地图；
- 18 岁以后内容生产；
- 广告、支付、账号和云存档；
- 为每项行动制作独立大插图。

### 13.3 四季度内容主题

#### Q1：入学准备与仍然想玩

候选方向：

- 练习写名字、认字和数数；
- 跟家人走一遍上学路线；
- 整理每天要带的东西；
- 听家人讲故事或问问题；
- 和附近孩子玩；
- 保留休息和自由时间。

验证：固定责任、2～3 项组合、时间/精力、学习与玩耍不互斥、家庭人物回应。

#### Q2：兴趣接触与生活习惯

候选方向：

- 画画、折叠、收集和比较物件；
- 跑跳、球类或简单户外游戏；
- 继续识字或数字练习；
- 承担一件家庭小任务；
- 和照看者一起处理生活小事；
- 主动休息。

验证：兴趣接触、身体节律、习惯、上一季度经历影响候选排序。

#### Q3：同伴、规则与随机事件

候选方向：

- 加入同伴游戏；
- 提议或改变游戏规则；
- 帮助/拒绝一名同伴；
- 继续学习准备；
- 完成家庭任务；
- 在疲劳时减少安排。

验证：持续人物、关系互动、随机事件、中断后剩余计划、人物记忆。

#### Q4：入学/在校适应与年度收束

候选方向：

- 适应课堂或学校规则；
- 跟同学共同完成小事；
- 继续已有兴趣；
- 平衡学习、玩耍和休息；
- 向家人讲述学校发生的事情。

验证：四季度因果、年度回望、未走道路、年龄 +1、7 岁身份/行动池、存档一致性。

### 13.4 首切片通过标准

必须全部满足：

1. 首次玩家在 30 秒内说清现在的年龄、季度和本季目标；
2. 3 分钟内能独立完成一个普通季度；
3. 普通季度能连续安排/执行至少两项行为；
4. 玩家不会把时间格理解为“一季度只生活几小时”；
5. 行动不是文字卡点击后等报告，而有立即可见反馈；
6. 玩家能说出至少两项行动的现实差异、成本和对象；
7. 早期行为能改变后续兴趣、人物、候选或事件；
8. 至少有一条资源不足或条件受限路径可正常解释；
9. 随机事件发生时，玩家知道它打断了什么、改变了什么；
10. Q4 后年龄确实增加并生成 7 岁入口；
11. 记录页可展开四季度事实；
12. 相同种子、内容版本和命令序列产生相同结果；
13. 保存、刷新和恢复不改变本季已提交事实；
14. 390×844 无横向溢出，重要按钮首屏可见；
15. reduced motion 和静音下可以完整游玩；
16. 自动检查与浏览器流程均通过；
17. 产品负责人在 Chrome 390×844 中完成 60～90 秒无剪辑实机流程，画面持续体现角色状态、行动留痕、反馈、时间推进和结果变化，而不是滚动文字、表单或 PPT；
18. 产品负责人可以亲自完成资源不足自救、事件打断、Q4 增龄和存档恢复。5～8 人外部测试为后续可选，不是当前个人开发硬闸门。

## 14. 技术架构与实现边界

### 14.1 技术路线

正式主玩法采用 Phaser/Canvas 2D 游戏运行时；DOM 只保留启动兼容、设置、长记录、调试、导入导出与可访问性辅助。技术目标为：

- TypeScript 严格模式；
- Vite；
- Phaser 3.90 游戏运行时；
- 纯 TypeScript 确定性 Core；
- GameGateway/应用层；
- DomainEvent → PresentationCue → Scene Director；
- IndexedDB 正式存档；
- JSON Schema 和内容包；
- 资源 manifest、Tween、音频和 reduced motion；
- Web Worker 作为长模拟的后续优化。

采用渐进替换：先建立薄的 Vite/TypeScript/Phaser 游戏壳，接现有 GameGateway 和 v5 存档，只迁移 1984 年 6 岁 Q1；通过实机游戏感闸门后再扩 Q2～Q4。不得一次性重写可工作的模拟 Core，也不得继续用旧 DOM 主屏验证“将来再游戏化”。

### 14.2 分层依赖

```text
Phaser/Canvas Game Runtime
  ↓ 提交稳定命令
Application / GameGateway
  ↓
Deterministic Core
  ↓
Domain Events + Snapshot
  ↓
Presentation / ViewModel / Cues
  ↓
Game Screens + Motion + Audio

DOM Utility Layer
  ↓ 同一 GameGateway
Settings / Records / Debug / Accessibility
```

- Core 不读取 DOM、localStorage、Phaser、素材路径、动画状态或当前屏幕；
- UI 不直接修改人物属性、兴趣、关系、现金或随机结果；
- presentation 不产生游戏事实；
- 动画、声音和震动只消费 cue；
- 所有内容使用稳定 ID；
- 不允许 `Math.random()` 影响游戏事实。
- Phaser Scene 不保存人生事实，也不直接读写正式存档；
- DOM 工具层不得另建一套模拟状态或主玩法。

### 14.3 季度命令建议

正式协议应保持兼容并逐步明确：

```ts
type GameCommand =
  | { type: "life.start"; config: StartLifeConfig }
  | {
      type: "quarter.plan";
      eventId: string;
      allocations: Array<{
        actionId: string;
        intensity: "trial" | "regular" | "focus";
      }>;
    }
  | { type: "event.choose"; eventId: string; optionId: string }
  | { type: "year.confirm"; year: number }
  | { type: "debug.advance"; target: DebugTarget };
```

UI 中逐个添加行动只是季度草案编辑，最终提交仍是一条 `quarter.plan`。若未来需要让离散行动在季度内立即成为不可撤销事实，应新增专门命令并升级存档，而不是让 UI 直接写状态。

### 14.4 存档

现有 v5 继续作为迁移输入。只有实现“季度进行中已提交的多条离散行动”时才升级 schema，不为纯界面草案无意义升级。

存档必须记录：

- schema、引擎和内容版本；
- 种子；
- 稳定命令日志；
- 最近 checkpoint；
- 当前 pending decision；
- 四季度事实；
- 事件选择；
- 人物关系和共同记忆；
- 未走道路；
- 调试存档与正式存档隔离。

### 14.5 当前代码的可复用部分

优先复用：

- `src/simulation/quarter-resource-system.mjs`：时间与精力；
- `src/simulation/quarter-month-simulator.mjs`：三个月实际执行；
- `src/simulation/quarterly-life-system.mjs`：季度行动候选与结算；
- `src/simulation/quarterly-random-event-system.mjs`：随机事件；
- `src/simulation/life-activity-process-system.mjs`：活动过程与共同记忆；
- `src/simulation/life-mainline-system.mjs`：人生方向；
- `src/game/game-engine.mjs`：命令、回放、存档迁移；
- `src/game/game-application.mjs`：应用层雏形；
- `src/game/debug-tools.mjs`：跳龄、事件和路线调试；
- `data/annual_life_operations.json`、`data/quarterly_life_content.json`、`data/childhood_play_content.json`：内容基础；
- 现有出生、教育、成年、职业、关系、住房、健康、退休和结局模拟。

停止扩大并逐步替换：

- `public/index.html`、`public/app.mjs`、`public/styles.css` 中的正式主玩法职责；这三者只允许迁移壳和必要修复；
- 网页卡片式主屏、底部抽屉式行动表单、通用 Toast 覆盖结果的交互；
- 继续通过 DOM 拼接增加年龄、模块、事件或结果页面；

需要新增/拆分：

- Vite/TypeScript/Phaser 正式游戏入口；
- `LifeScreen`、`ActionPanel`、`EventScreen`、`QuarterResultScreen`、`YearReviewScreen`；
- GameGateway → PresentationCue → Scene Director 的适配层；
- 主屏 ViewModel 与短反馈 cue；
- 素材 manifest、头像、图标、动画和声音管理；
- 浏览器回归截图和交互路径。

停止扩大：

- `public/light-scene/`；
- `src/game/light-scene-*`；
- `data/gameplay/light_scene_yard_1984.json`；
- 场景热点、对象发现、节点移动和旧轻场景 Spike。

### 14.6 性能目标

- 390×844 中端手机保持流畅操作；
- 输入反馈尽量在 100ms 内可见；
- 普通转场 900ms 内结束且可跳过；
- 首屏只加载当前年龄所需头像、模块图标和氛围图；
- 非当前年龄内容延迟加载；
- 图片失败、声音失败和动画关闭均不阻断游戏；
- 长人生结算迁入 Worker 前先用真实性能证据证明必要性。

## 15. 内容生产规范

### 15.1 不以事件数量冒充内容质量

一项内容只有同时具备“对象、成本、过程、回应、即时变化和长期钩子”才算可玩内容。仅有标题、两段说明和 `属性 +1` 的条目不算完成。

### 15.2 内容层级

- 普通行动：高复用、短反馈、可重复但有衰减；
- 人物互动：读取人物状态与共同记忆；
- 随机事件：条件化、低频、打断或改变计划；
- 关键事件：人生道路改变；
- 年代事件：改变多个系统的机会与成本；
- 长期回响：几年后兑现过去行为；
- 章节回望：把事实组织成玩家能够理解的人生因果。

### 15.3 年龄内容扩展顺序

不得从 6 岁切片直接批量铺满整生。按以下代表节点验证：

1. 6 岁：学习、玩耍、家庭、同伴、兴趣；
2. 18 岁：升学/就业入口、金钱、迁移、关系与机会成本；
3. 30 岁：职业、伴侣/单身、住房、育儿和资产冲突；
4. 45 岁：职业变化、父母/子女照护、健康和重新选择；
5. 65 岁：退休、身体、家庭、社会参与和传承；
6. 完整结局：一生因果、重要人物和未走道路。

每个代表节点通过后，才批量迁移相邻年龄内容。

## 17. 多代理开发规则

下一次正式开发必须遵循项目 `AGENTS.md`，并采用制作人制多代理分工。

### 17.1 主代理职责

- 冻结协议和产品判断；
- 拆分批次、文件所有权和验收标准；
- 审查子代理产物并处理冲突；
- 运行最终验证；
- 决定是否进入下一闸门；
- 不把“是否好玩”“是否完成”外包给子代理。

### 17.2 模型使用

- 边界清楚、独立验收的任务优先 `gpt-5.6-luna`；
- Luna 缺少必要能力、两次修订仍不合格或无法保持跨文件一致性时升级 `gpt-5.6-terra`；
- 复杂核心协议、高风险集成或 Terra 仍无法可靠完成时才使用 `gpt-5.6-sol`；
- 升级必须保留失败证据和已有产物，不得无证据从头重做。

### 17.3 推荐分工

同一批次可并行：

- 产品/内容代理：行动、事件、人物和文案数据；
- 模拟代理：Core、命令、确定性和存档；
- UI 代理：主屏、模块、互动层和响应式；
- 美术/动效代理：素材、cue、动画和声音；
- QA 代理：自动检查、Chrome 实机流程、截图、录屏和恢复证据。

共享协议、存档版本、全局样式、稳定 ID 目录和依赖只能有一名所有者。禁止多个代理同时修改同一文件。

## 19. 主要风险与停止条件

### 风险 1：再次退化成文字卡列表

信号：行动主要通过长段说明区分，玩家没有注意人物、资源、模块和即时反馈。

处理：停止扩内容，先修复信息层级、行动模板和反馈。

### 风险 2：用动画掩盖没有玩法

信号：按钮很流畅，但不同选择只改变几个数值。

处理：补充对象、过程、人物回应、条件和长期钩子，不继续增加装饰动画。

### 风险 3：模拟过细造成 300 多轮疲劳

信号：普通季度需要十几次点击，一年超过数分钟且没有新决策。

处理：自动延续、快速结算、阶段性操作量和只在关键事件打断。

### 风险 4：模拟过粗导致选择虚假

信号：所有行动都只是属性加减，现实条件和人物没有作用。

处理：让行动读取真实身份、时间、金钱、关系和历史条件，并提供受限路径。

### 风险 5：继续扩网页代码，迟迟没有游戏运行时

信号：继续大量修改 `public/index.html`、`public/app.mjs`、`public/styles.css`，画面仍靠卡片、抽屉、滚动和文字结果成立。

处理：停止旧 DOM 主玩法开发，只建立薄 Phaser 游戏壳并接现有 Gateway；先完成一个可录屏的 6 岁季度，再扩客户端结构。

### 风险 6：一次铺满整个人生

信号：大量年龄内容都只有标题和结果文字。

处理：严格按 6→18→30→45→65→结局的代表切片闸门推进。

停止条件：如果 6 岁切片经过两轮明确修订后，产品负责人在 Chrome 无剪辑实机流程中仍认为它只是文章、网页、表格或 PPT，停止全人生扩展，重新评估主循环与表现层，不得靠增加内容数量掩盖问题。

## 21. 最终制作人结论

《1978—一生》接下来不需要更大的地图，也不需要更多网页代码和文章。它需要把已经存在的季度模拟核心，通过正式游戏运行时呈现成一款有角色、有行动留痕、有即时演出、有时间推进和长期反馈的人生模拟游戏。

正确方向可以概括为：

```text
以人生为主线
+ 以季度为回合
+ 以生活模块组织行动
+ 每季度连续执行多项具体行为
+ Phaser/Canvas 游戏屏幕承载角色、行动和结果
+ 人物、资源、动画、声音和短记录立即反馈
+ 真实社会事实限制机会
+ 兴趣、关系、习惯和能力长期积累
+ 年度与结局解释一生因果
- 场景移动
- 热点寻找
- 长文字堆砌
- 网页档案、仪表盘和表单式主玩法
- 继续膨胀 index.html / app.mjs / styles.css
```

先把 1984 年 6 岁的一年做成真正可玩的游戏切片，再扩展一生。
