# 《1978—一生》产品方向重置、客户端架构决策与首个垂直切片

状态：**待项目负责人批准技术迁移，不授权直接开发**  
日期：2026-08-23  
适用范围：TapTap 目标产品、浏览器试玩版、客户端表现层、场景与玩法生产  
替代范围：本文件否定旧文档中“以 DOM 卡片、静态背景和 CSS 动效即可完成全面游戏化”的结论；旧文档仍可作为模拟规则和历史数据参考。

> **2026-08-23 补充决策：** 项目负责人已确认下一步制作真实可玩切片，但明确不做大地图自由移动。首切片改为“固定舞台＋对象热点＋节点转场＋短互动演出”，直接全面迁移 Phaser 暂停，先进行 DOM SceneRuntime 与 Phaser 的同规格技术 Spike。正式开发规格以 [《轻场景互动垂直切片开发说明》](LIGHT_SCENE_VERTICAL_SLICE_DEVELOPMENT_PLAN.md) 为准。

## 0. 决策摘要

当前版本不是目标中的场景化人生游戏，而是一个完成度较高的确定性人生模拟核心，加上网页式文字交互外壳。继续增加卡片、插图、背景缩放、结果文字和页面动画，不会跨越这一产品形态差距。

本文件建议作出以下决策：

1. 产品定位由“竖屏文字人生模拟”调整为“以角色行动和生活场景为主体、以季度为宏观时间单位的人生模拟 RPG”。
2. 冻结新增年龄、行动、事件和旧界面美化，直至首个真实可玩场景通过盲测。
3. 保留确定性模拟、历史数据、命令、存档、调试与批量校准能力。
4. 不再以 DOM 页面作为主要游戏舞台；推荐用 Phaser 建立 H5 2D 场景运行时，DOM 只保留设置、记录、存档和无障碍辅助层。
5. 先制作“1984 年，6 岁，放学后的院子”单场景垂直切片，不直接迁移整个人生。
6. 只有切片被首次玩家识别为“正在操控角色生活”，而不是“选择文字看结果”，才进入第二个 18 岁切片和全人生生产。

在项目负责人明确批准第 4 项前，不安装 Phaser、不迁移代码、不废弃现有客户端。

## 1. 为什么必须重置方向

### 1.1 当前产品实际是什么

当前实现拥有以下真实价值：

- 同一种子、内容版本和命令序列可以复现同一人生；
- 已覆盖出生、教育、工作、关系、家庭、住房、健康、退休和死亡；
- 有季度时间、属性、兴趣、长期因果、存档、调试跳龄和批量模拟；
- 历史观测、模型假设和玩法内容能够分离；
- 浏览器运行稳定，主要流程可自动检查。

但玩家实际执行的主要操作仍是：

```text
阅读说明 → 浏览文字行动 → 选择投入 → 点击结算 → 阅读结果
```

这是一种文字模拟器闭环，不是场景化生活游戏闭环。

目标闭环应该是：

```text
进入生活场景 → 观察人物和物件 → 移动/接近 → 执行动作
→ NPC 与环境回应 → 当下局面改变 → 长期人生状态留下影响
```

### 1.2 结构性问题与表面问题

以下是结构性问题，不能通过换色、加阴影、增加图片或优化排版解决：

- 玩家没有在世界中的可控角色实体；
- 背景图不负责空间、入口、碰撞、交互和状态；
- 行动没有靠近、准备、执行、回应和余波；
- NPC 没有位置、作息、目标、情绪和当前行为；
- 没有角色动画状态机、场景对象、镜头导演和声音层；
- 大多数反馈发生在结算文字中，而不是游戏世界中；
- 五个主页面采用网站信息架构，而不是围绕当前生活处境组织；
- 内容量已经远超表现层承载能力。

以下只是表面问题，处理后也不会让产品自动成为游戏：

- 卡片颜色老旧；
- 字体不够活泼；
- 背景图数量不足；
- 页面切换不够顺滑；
- 按钮缺少弹性动画；
- 结算数字缺少跳动。

## 2. TapTap 同类产品对照

### 2.1 最接近当前形态的产品

| 产品 | 当前版本与它的相似点 | 对项目的结论 |
| --- | --- | --- |
| [人生重开模拟器](https://www.taptap.cn/app/223281) | 属性分配、文字事件、短人生结算、反复重开 | 这种形态可以支撑几分钟一局的病毒式轻游戏，但开发者也把原网页版本描述为几乎算不上游戏，不能直接证明它能承载数百季度的沉浸体验 |
| [人生模拟器－养育篇](https://www.taptap.cn/app/840309) | 大量事件、多结局、以文字为主体 | 属于创意工坊式轻量文字模拟。如果本项目选择这条路线，就应缩短单局、强化重开和荒诞组合，而不是同时追求长线场景体验 |

结论：当前版本在市场上并非没有同类，但会被归入低成本、轻量、文字模拟的产品组，而不是场景化人生游戏。

### 2.2 更接近目标定位的产品

| 产品 | 有效做法 | 对本项目的启示 |
| --- | --- | --- |
| [未来人生](https://www.taptap.cn/app/230041) | 人物立绘、场景、地图、差异职业、创业、宠物、战斗与小游戏 | 长线人生不能只靠事件数量，需要地图、人物和不同生活领域的具体玩法；其[玩家评价](https://www.taptap.cn/app/230041/review?os=android)也同时提醒重复内容仍会快速暴露 |
| [属性与生活3](https://www.taptap.cn/app/197714) | 房屋和城市中的电脑、炉灶、浴室、公园等具体对象承载行动 | 即使预算不高，也可以让玩家围绕物件产生动词，而不是把所有动词写成列表 |
| [众生游](https://www.taptap.cn/app/15444/topic) | 角色、场景、物品和家庭处境共同形成玩家故事 | 场景能产生参与感；但企图精确模拟整个人生所有机制也会变得臃肿，因此必须先验证少量高质量生活片段 |
| [古代人生](https://www.taptap.cn/app/180772) | 治理、婚礼、打猎、种田、科举等采用不同玩法模块 | “再加一些职业和事件”不是解法，人生领域需要可以被操作的玩法语法 |

### 2.3 平台展示风险

TapTap 的广告素材审核规范将纯图片逐张切换的视频描述为类似 PPT、制作质量较低。该规范针对广告素材，不等同于游戏 UI 审核规则，但它说明当前产品即使功能完整，也很难通过商店截图和短视频让玩家感知到“可以玩”。来源：[TapTap 广告审核规范](https://biz.taptap.cn/docs/res/TapTap_Review.pdf)。

首发宣传视频至少必须能够展示：

- 角色在场景中移动；
- 与人物或物件发生动作；
- NPC 与环境作出可见回应；
- 同一个地点因选择发生改变；
- 一次当下行为如何进入长期人生。

如果视频只能展示换页面、选卡片和数字变化，说明产品仍未越过文字模拟器边界。

## 3. 当前界面的处置决定

| 当前界面 | 主要失败点 | 处置 |
| --- | --- | --- |
| 标题页 | 静态海报、长说明、单按钮，缺少立即可玩的角色与环境 | **完全重做**。改为短主菜单＋动态生活片段；10 秒内进入可操作场景 |
| 创建人生 | 年份、风险偏好等参数表单化 | **大幅压缩**。只保留会改变规则的必要设置，其余由出生演出和家庭场景揭示 |
| 出生/开年 | 用档案文字描述家庭和时代 | **重做为演出**。用房间、照护者、声音和物件展示家庭处境，详细数据进入记录页 |
| 人生/场景页 | 背景是壁纸，人物不能独立活动，行动仍是文字条 | **完全替换为游戏场景**。这里必须成为主要游玩时间所在 |
| 行动池 | 展开大量文字项、精确收益预览、同构选择 | **取消全量首屏展示**。可行动对象存在于场景；复杂计划只在暂停/规划层出现 |
| 投入强度 | 分段按钮选择，仍是网页控件 | **改为时间与体力分配**。拖动、排入时间段或在现场继续/停止，不作为独立表单页 |
| 随机事件 | 弹窗、插图、文字选项 | **改为场景事件**。优先由人物靠近、物件变化、镜头和对白触发；只有无法空间化的事件才使用短弹层 |
| 季度结算 | 行为发生在屏幕后，结果以报告揭示 | **压缩为短回放**。先显示场景余波和人物回应，再以少量图标收束长期变化 |
| 年度回望 | 重复季度信息，阅读负担高 | **保留但降频**。改为可跳过的四季蒙太奇，详细账本进入记录页 |
| 地图 | 地点图标列表，不是空间 | **重做为地点网络**。可选择出行，但进入地点后必须是可交互场景；不伪造开放世界 |
| 角色 | 属性仪表盘和裁切头像 | **改为角色界面**。全身外观、穿着、当前状态、兴趣表现和可装备/持有物优先，数值为次级信息 |
| 关系 | 人名列表、头像和数值 | **重做为人物网络**。显示对方当前所在、情绪、最近共同经历和可发起的具体互动 |
| 人物详情 | 档案文章，没有当下互动 | **改为人物互动层**。对话、邀请、帮助、冲突、共同活动必须回到场景执行 |
| 记录 | 档案、账本、时间线 | **保留**。这是唯一允许高文字密度的主功能，不再让其视觉语言覆盖全游戏 |
| 结局 | 文字总结和数值复盘 | **重做为人生蒙太奇**。关键场景、重要人物、选择代价和未走道路形成情绪高潮 |
| 设置 | 普通网页对话框 | **保留工具职责**，只需统一视觉和动效设置 |
| 调试 | 开发控制面板混入玩家界面 | **保留为独立工具应用/抽屉**，正式构建不显示 |

处置原则：记录和调试可以继续使用 DOM；人物生活、事件和主要行动不能再由 DOM 卡片主导。

## 4. 客户端技术架构决策

### 4.1 备选方案

| 方案 | 优点 | 关键问题 | 结论 |
| --- | --- | --- | --- |
| 继续原生 DOM/CSS/Canvas 补丁 | 改动小、现有测试可直接复用 | 架构继续鼓励页面、卡片和滚动；角色、场景、相机和动画要自行拼装 | **否决作为主游戏舞台** |
| Vue＋DOM 动效 | 工程拆分、设置/记录类页面更易维护 | 解决代码组织，不解决游戏世界；仍容易做成精致网页 | **仅用于工具与辅助界面** |
| PixiJS | 高性能 2D 渲染、场景树、资源和精灵支持好 | 输入、场景生命周期、动画组织、相机和常用游戏结构需要项目自行搭建 | **可行但不优先** |
| Phaser | H5 2D 场景、精灵、动画、输入、相机、音频、粒子和资源系统完整；可继续使用 TypeScript/JavaScript 核心 | 客户端表现层需要较大重写，必须防止把模拟规则塞进 Scene | **推荐** |
| Godot 4 | 完整 2D 编辑器、场景节点、TileMapLayer、动画和调试体验 | 现有 JS 核心需要移植或桥接；Web 导出依赖 WebAssembly/WebGL2，首发包与平台兼容验证更重 | **若未来转原生优先才重新评估** |

Phaser 的场景、输入、相机、动画和音频能力可参见[官方文档](https://docs.phaser.io/)与[场景系统](https://docs.phaser.io/phaser/concepts/scenes)。Godot Web 导出的当前约束参见[官方文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)。

### 4.2 推荐架构

```text
TapTap / Web 启动层
        │
        ▼
Game Application / Command Gateway
        │
        ├──────────────► Save / Settings / Platform Adapter
        │
        ▼
确定性人生模拟 Core ──► Domain Events / Snapshot
        │                          │
        │                          ▼
        │                  Presentation Cue Mapper
        │                          │
        │                          ▼
        │                   Phaser Scene Director
        │                   ├─ 场景与相机
        │                   ├─ 玩家与 NPC
        │                   ├─ 动画与动作编排
        │                   ├─ 可交互物件
        │                   ├─ 环境/声音/VFX
        │                   └─ 游戏 HUD
        │
        └──────────────────► DOM Utility Layer
                            ├─ 设置
                            ├─ 记录/账本
                            ├─ 存档
                            ├─ 无障碍替代操作
                            └─ 调试工具
```

### 4.3 保留、迁移与废弃范围

**完整保留：**

- `src/simulation/` 的确定性规则和 RNG 原则；
- 稳定 ID、命令日志、Domain Event 与 checkpoint 思路；
- `data/calibration/`、主要玩法数据、存档迁移和批量校准；
- 调试跳龄、事件定位、存档导入导出；
- 动画不能决定模拟事实的边界。

**逐步迁移：**

- application/game gateway 变成引擎无关接口；
- presenter 从“生成整页文案”变成“把事实映射为短表现提示”；
- 关系、兴趣、时代和任务数据提供给场景 Director；
- 当前浏览器调试台独立成工具入口。

**停止扩大：**

- `public/app.mjs` 中的整页拼接；
- 以 CSS 卡片状态承担主要玩法；
- 把一张背景图加缩放称为可玩场景；
- 为每个行动继续增加结果文章；
- 继续制作仅能作为卡面或壁纸的孤立插图。

### 4.4 场景数据契约

每个生产场景必须至少提供：

```ts
interface LifeSceneDefinition {
  sceneId: string;
  eraBand: string;
  ageBand: string;
  entryPoints: SceneEntryPoint[];
  walkableRegions: WalkableRegion[];
  collisionShapes: CollisionShape[];
  interactables: SceneInteractable[];
  npcSpawns: NpcSpawn[];
  npcSchedules: NpcSchedule[];
  cameraZones: CameraZone[];
  ambientLayers: AmbientLayer[];
  audioCues: AudioCue[];
}
```

硬性规则：

- 背景图只负责视觉，不负责碰撞、交互和游戏事实；
- 玩家出生点、门、NPC、路线和交互物必须是独立标记或对象；
- 隐藏全部装饰图层后，移动、碰撞、交互和进出场景仍然有效；
- 重复且有行为的家具、门、桌子、商店、交通工具必须是可复用 Prop；
- Core 决定结果，Scene Director 表现结果，动画播放失败不得改变人生事实。

### 4.5 迁移方式

采用渐进替换，不一次性推倒：

1. 冻结旧客户端功能扩张；
2. 抽出稳定 `GameGateway`，让旧界面与新场景读取同一快照；
3. 新建独立 `apps/game-prototype` 或等价入口，只实现垂直切片；
4. 垂直切片通过后，再决定将其作为正式客户端还是停止迁移；
5. 旧 DOM 应用保留为模拟验证、内容查看和调试工具；
6. 第二个 18 岁切片通过后，才迁移完整人生章节。

## 5. 首个垂直切片：1984 年，6 岁，放学后的院子

### 5.1 验证目标

这个切片不是展示美术，而是验证四件事：

1. 玩家能否感觉“我就是这个孩子”；
2. 行动能否主要通过人物、地点和物件发起；
3. 一个短场景能否同时影响兴趣、智力、健康和关系；
4. 当前行为能否自然进入季度和长期人生，而不靠长篇解释。

### 5.2 时间结构

- 宏观：每自然年仍为四个季度；
- 中观：一个季度由三个“生活片段”代表三个月的高参与时刻；
- 微观：一个生活片段约 5～8 分钟，包含 3～5 次具体动作；
- 日常上学、吃饭、睡眠等稳定责任通过短蒙太奇推进，不要求玩家机械点击；
- 本垂直切片只实现一个生活片段，季度后续两个片段使用占位结果，不扩张内容。

这种结构保留季度模拟，又避免“一次点击直接过去三个月”和“一年点击几十次”两个极端。

### 5.3 场景设定

时间：1984 年初秋，放学后约 45 分钟。  
地点：城市或县城家属院；首版固定一种家庭背景，避免为城乡差异同时制作两套场景。  
角色：6 岁主角、照护者、邻居同龄伙伴、年龄稍大的孩子。  
当前处境：入学后不久，主角第一次可以自行决定放学后的一小段时间。

场景区域：

1. 院门与回家路线；
2. 石桌与识字本；
3. 空地与弹珠/跳格子；
4. 家门与需要帮忙摆放的碗筷；
5. 自行车棚或花坛，提供观察和探索对象。

### 5.4 玩家动词

首版只允许以下高复用动词：

- 移动；
- 观察；
- 交谈；
- 加入；
- 帮助；
- 练习；
- 离开/停止。

每个动词必须有动作、对象回应和世界状态变化，不能只打开一段解释。

### 5.5 可执行行动

| 行为 | 场景执行 | 当下反馈 | 长期事实候选 |
| --- | --- | --- | --- |
| 加入伙伴玩弹珠 | 走近、询问、蹲下、瞄准、投掷 | 伙伴让位、弹珠移动、胜负与表情 | 身体节律、同伴关系、玩耍兴趣、可能弄脏衣物 |
| 在石桌练习识字 | 坐下、翻本、描字、被人打断或得到提示 | 字迹、角色专注动作、照护者/伙伴评价 | 理解求知、智力残差、学校适应、错过同伴活动 |
| 回家帮助摆碗筷 | 进门、拿取、摆放、与照护者短对话 | 桌面物件逐一改变、照护者态度变化 | 家庭参与、关系、责任习惯、剩余自由时间减少 |
| 观察自行车链条 | 靠近、蹲下、触碰或询问年长孩子 | 链条转动、手沾油、获得解释或被制止 | 动手兴趣、认知、轻微受伤/弄脏风险 |

玩家不能在一个静态列表中同时看到全部行动。可操作对象通过轮廓、角色视线、环境动作或短提示被发现；辅助模式可以提供对象列表。

### 5.6 动态事件

事件：伙伴的一颗弹珠滚进自行车棚附近。

事件不弹出文章，而是在场景中真实发生：

1. 弹珠滚动并停下；
2. 伙伴移动、寻找并表现焦急；
3. 玩家可以帮助寻找、继续玩、询问年长孩子或离开；
4. 不同做法改变关系、时间、弄脏/受伤风险和可获得的动手经验；
5. 结果由模拟 Core 生成，场景只负责演出。

### 5.7 回合、时间与体力

该切片使用可见但不过度数字化的资源：

- `时间段`：放学后 45 分钟，分成 9 格，每格约 5 分钟；
- `体力`：使用全人生统一 0～100 体力属性，但本场景消耗的是短期精力，不重置或校准长期属性；
- `专注`：不新增终身属性，只由疲劳、心情、健康和当前干扰派生；
- 移动和观察消耗很少，完整活动消耗 2～4 个时间格与相应精力；
- 玩家可以随时停止行动，保留部分进展，不必每次先填写投入强度表单；
- 时间将尽时由天色、家人呼唤和 HUD 同时反馈，不只显示红色数字。

### 5.8 画面与交互布局

390×844 竖屏首要布局：

```text
┌──────────────────────┐
│ 年份 / 年龄 / 剩余时间 │  小型 HUD
├──────────────────────┤
│                      │
│      可玩场景         │
│  玩家 / NPC / 物件    │  约占 70% 高度
│                      │
│   就地短对白与反馈     │
├──────────────────────┤
│ 当前对象：交谈 / 加入  │  情境操作条
└──────────────────────┘
```

规则：

- 场景游玩时不显示五栏底部导航；暂停后才能进入角色、关系、记录和设置；
- 连续对白最多两行，详细原因进入回顾；
- 不显示精确的 `智力 +0.37` 预告，只显示倾向、风险和角色可理解的信息；
- 结果首先由角色、NPC 和物件表现，数值图标随后短暂出现；
- 鼠标点击、触摸点击和键盘方向输入使用同一交互语义；
- 必须支持减少动态效果、静音和无需精确拖动的替代操作。

### 5.9 最低动画与声音清单

主角动画：

- idle、walk、turn、inspect、talk、sit/write、crouch/play、carry/place、happy、disappointed；

NPC 动画：

- idle、walk、talk、invite、search、approve/disapprove；

环境动画：

- 树叶/衣物轻动、弹珠滚动、自行车轮/链条、门开关、桌面物件变化、傍晚光线变化；

声音：

- 院落环境、脚步、门、弹珠碰撞、翻纸/铅笔、碗筷、家人呼唤、短反馈音；

镜头：

- 进入场景、事件聚焦、动作轻跟随、季度片段结束；不使用持续无意义漂移。

### 5.10 美术生产规则

- 先用灰盒验证比例、移动和热点，再绘制最终场景；
- 背景分为远景、建筑/墙、地面、前景遮挡，功能物件独立；
- 人物使用统一比例的精灵表，不把不同透视的立绘直接贴在背景上；
- 碰撞、行走区、入口和交互区使用独立数据；
- 场景在隐藏全部视觉参考图后仍可完整游玩；
- 首个切片优先使用帧动画精灵表，不立刻引入昂贵骨骼动画管线；
- 任何 AI 生成图只作为概念或可拆分素材来源，不能直接充当玩法事实层。

### 5.11 切片不包含的内容

- 不实现完整 0～6 岁；
- 不实现城乡两套院落；
- 不实现开放世界或连续城市地图；
- 不实现完整换装、战斗、社交网络和经济系统；
- 不迁移全部 97 项行动；
- 不制作年度结局和多周目；
- 不为每个属性制作独立小游戏；
- 不以“未来可扩展”为理由提前加入后端、账号或平台 SDK。

## 6. 垂直切片验收门槛

### 6.1 产品门槛

- 新玩家进入后 60 秒内控制角色完成第一次具体行为；
- 首次玩家无需阅读说明，能发现至少 3 个可交互目标；
- 一次完整行动包含“靠近—执行—回应—状态变化”；
- 玩家游玩时间至少 75% 停留在场景，而不是菜单和报告；
- 一个生活片段内至少出现 1 次 NPC 主动行为、1 次环境变化、1 次长期结果提示；
- 结算正文不超过 80 个汉字，详细数据只在记录页展开；
- 不看数值面板，玩家也能描述自己刚才做了什么、谁对此作出了反应；
- 场景结束后玩家可以明确说出至少一个想尝试的不同做法。

### 6.2 盲测门槛

至少邀请 5 名未参与设计的人完成首次试玩：

- 4/5 能在无口头指导下完成两个不同动词；
- 4/5 将核心体验描述为控制人物、探索或生活，而不是阅读文章；
- 至少 3/5 主动选择重玩或询问另一条行为结果；
- 将产品形容为“PPT/网页/选文字”的人数不得超过 1/5；
- 平均“我能感到自己在扮演这个孩子”评分不低于 4/5。

若未通过，不允许用增加剧情和行动数量掩盖问题；必须回到操控、场景、反馈和可读性修正。

### 6.3 技术门槛

- 390×844 中端移动设备目标 60fps，压力场景最低不低于稳定 30fps；
- 点击/触摸后 100ms 内出现视觉或声音响应；
- 场景切换目标不超过 1.5 秒，慢设备有明确加载反馈；
- 刷新或恢复存档后，场景物件与已经发生的事实一致；
- 关闭动画、静音和减少动态不改变模拟结果；
- 同种子和同命令仍产生同一 Core 结果；
- 浏览器控制台无错误，触摸目标可达，无底部导航遮挡；
- 视觉背景隐藏后，碰撞、入口、交互和事件仍然可验证。

## 7. 分阶段开发闸门

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| G0 方向批准 | 本文档、竞品判断、架构决策 | 项目负责人明确选择场景化路线并批准 Phaser 技术验证 |
| G1 无美术灰盒 | 可移动角色、碰撞、4 个物件、3 个 NPC、事件骨架 | 10 分钟流程完整，无文字卡替代动作 |
| G2 美术与动作切片 | 统一人物、分层院落、动作、环境、声音 | 达到产品与技术门槛 |
| G3 首轮盲测 | 5 名首次玩家记录、录像/观察、问题清单 | 达到盲测门槛；否则回到 G1/G2 |
| G4 第二切片 | 18 岁升学/工作/家庭冲突场景 | 同一架构能承载成年压力、金钱和关系 |
| G5 章节生产 | 优先制作 6、12、18、30、50、70 岁关键章节 | 两个切片均通过，内容工具和资产管线稳定 |
| G6 平台化 | TapTap 构建、登录/存档/审核与发布适配 | 完整章节、性能、内容审核和留存验证通过 |

### 粗略工作量级（个人学生开发，非工期承诺）

- 无美术技术灰盒：约 2～4 周；
- 有统一角色、场景、动作和声音的首个切片：约 4～8 周；
- 第二个成年切片：约 3～6 周；
- 达到可公开测试的多个关键年龄章节：通常需要 6～12 个月；
- 从出生到老年的高一致性完整产品：更可能是 12～24 个月以上的范围。

如果没有稳定的美术与动画协作者，必须减少场景数量、角色数量和独立动作，而不能重新退回文字卡片冒充内容完成。

## 8. 立即停止与允许继续的工作

### 立即停止

- 新增年龄段、职业、事件和行动数量；
- 继续美化现有卡片、网页导航和长结算；
- 把背景缩放、面板滑入和数值跳动统计为“完整动画”；
- 在场景契约确定前继续生成整张 AI 背景；
- 宣称当前版本已经完成游戏化或具备发布品质；
- 用自动化流程通过代替真实玩家可玩性验证。

### 允许继续

- 修正文档中的错误状态和过时结论；
- 维护确定性 Core 的正确性和现有存档安全；
- 将旧客户端作为调试/内容查看器保留；
- 制作单场景灰盒、交互契约和资产清单；
- 进行 TapTap 竞品试玩、录屏拆解和首次玩家测试；
- 在明确批准后进行 Phaser 独立技术验证，不直接改写正式客户端。
