## 2. 项目总目标

把当前确定性人生模拟原型开发成可在 TapTap H5 发布的中文竖屏季度回合制人生模拟游戏：

- 以角色一生为主线，以季度为回合；
- 玩家持续看见年龄、身份、角色、资源、近期人生和当前季度安排；
- 学校、活动、关系、家庭、生活/资产是游戏模块；
- 选择具体行动后，行动持续留在本季度安排中并立即产生反馈；
- 每季度只有一个明确的结束/推进动作；
- 三个月执行、资源不足、事件打断、季度结果、Q4 增龄和长期因果都有可观察的游戏表现；
- 参考《中国式人生》的游玩语法，不复制其美术、文案、数值、素材或代码；
- 不做角色移动、地图、热点寻找、寻路、碰撞或 3D；
- 不把滚动网页、仪表盘、表单、背景图和文字卡当作游戏完成；
- 保留并复用现有确定性 Core、季度月份模拟、兴趣、关系、长期因果、v5 存档和调试；
- 正式主玩法通过 Phaser/Canvas 2D 游戏运行时呈现，DOM 只承担工具职责。

最终完成不是“代码写完”，而是形成可构建、可真机试玩、可恢复存档、可通过发布检查并可提交 TapTap 审核的发布候选。

### 3.2 从错误方向得到的永久结论

1. **架构不是“只能做网页”。** 浏览器和 H5 只是容器；Phaser/Canvas 足以承载正式 2D 游戏。此前像网页，是因为信息架构和交互被设计成网页，不是 HTML 技术天然做不到游戏。
2. **换引擎本身也不会自动变成游戏。** 把原来的文字卡原样搬到 Canvas，或加入背景图、淡入淡出和按钮音效，仍可能只是 PPT。
3. **游戏感不等于角色移动。** 本项目的核心参与感来自角色状态、行动留痕、资源取舍、人物回应、月份推进、事件打断和长期兑现，不来自在场景里走路找热点。
4. **内容数量不能掩盖交互失败。** 新增更多事件、职业、年龄文字，只会放大重复和阅读负担；代表切片未通过前禁止铺满整生。
5. **自动检查只能证明功能证据。** 自动化可以证明按钮在特定坐标可触发、存档可恢复、Q4 可增龄；它不能代替产品负责人判断按钮是否自然、界面是否像游戏、是否愿意继续玩。
6. **素材和动画必须服务于行动。** 一张漂亮背景、人物立绘、转场或文字特效，只有在玩家选择、人物反应和事实变化形成闭环时才是游戏表现。
7. **测试工具不得主导产品。** 5～8 人盲测已降为后续可选；当前个人开发由产品负责人在 Chrome 手动验收。不能为了脚本方便改变正式 UI，也不能用测试 fixture 冒充完整正式游玩。

## 4. 冻结的玩家体验

### 4.1 目标玩家动词

- 查看角色与当前人生；
- 切换生活模块；
- 选择具体行动；
- 调整行动投入；
- 撤销未提交行动；
- 处理人物与随机事件；
- 结束本季度；
- 查看三个月过程和季度结果；
- Q4 后确认年度回望并进入下一年龄。

移动、找热点、猜背景点击、阅读长篇结果和填写表单不是基本动词。

### 4.2 390×844 主屏冻结

无需纵向滚动即可看到：

1. 年份、年龄、季度、身份和关键资源；
2. 持续可见的玩家角色、当前状态和一句回应；
3. 最近 1～2 条人生变化；
4. 学校/学习、活动/兴趣、关系、家庭、生活/资产模块；
5. 当前季度已经选择的行动、对象、投入和成本；
6. 唯一的“结束本季度”主动作。

行动选择规则：

- 点击行动后立即进入当前季度安排，不得消失；
- 不使用“加入本季 → 完成选择 → 安排本季度”三层确认；
- 资源不足时说明具体缺口，允许返回调整；
- UI 可以立即表现按压、角色反应和资源预留，但属性、关系和兴趣的最终事实必须由 Core 产生；
- 事件、季度结果和年度回望使用独立游戏屏幕，不用 Toast 遮挡结果。

### 4.3 最低游戏表现

P1/P2 不能只交付灰色矩形和说明文字，至少需要：

- 玩家角色或半身形象；
- 统一游戏 UI 材质、图标和状态语言；
- 行动进入季度安排的可见动画；
- 资源预留/不足反馈；
- 人物表情或姿态反馈；
- 月份推进、事件聚焦、季度完成和 Q4 增龄转场；
- 基础 UI 音效，且支持静音；
- reduced motion 下仍可完整操作。

## 5. 技术边界

```text
Deterministic Core
  → Application / GameGateway / Save
  → Snapshot + Domain Events
  → Presentation Cue Mapper
  → Phaser/Canvas Game Runtime
  → DOM Utility Layer
```

硬规则：

- `src/simulation/` 不读取 DOM、Phaser、存储、动画或素材路径；
- Phaser Scene 不计算人生规则、不产生随机事实、不直接写存档；
- Game Runtime 只消费 snapshot/cue 并提交稳定命令；
- 动画、声音和震动不决定结果；
- 正式游戏素材全部通过稳定 manifest key 引用；
- `public/index.html`、`public/app.mjs`、`public/styles.css` 只允许兼容和必要修复；
- 新正式主玩法进入独立 Vite/TypeScript/Phaser 目录；

#### 8.5.3 冻结的低保真游戏流程

390×844 不使用 DOM 长页面、通用 Toast 或底部抽屉承载 P2 主流程：

1. `LifeScene`：沿用 P1 持续角色、四个安排槽、五模块、2×2 图像行动牌和唯一季度推进键；Q2/Q3/Q4 逐季重新进入，不瞬间跳过；
2. `EventScene`：顶部保留年份/年龄/Q/月，画面聚焦人物或处境，标题与一句场景短句，直接显示 2～3 个游戏选项；选择前必须看清发生月份和可能影响，不用 Toast；
3. `QuarterExecutionScene`：三个月轨道逐格推进，显示行动 token 的执行/中断状态、角色反应和资源变化；Core 已经确定全部事实，玩家可跳过演出；
4. `QuarterResultScene`：一屏显示本季主要行动、执行率、资源结果、人物/兴趣/成长变化和事件打断，只保留一个“进入下一季度/查看年度回望”动作；
5. `YearReviewScene`：四季度可视轨道、最多五项年度重点、未走道路入口与明确的“进入 7 岁”；不得用长报告或 Toast 遮挡；
6. `AgeEntryScene`：用年龄、身份、角色和模块变化表现 6→7 岁，确认后进入 7 岁生活主屏；
7. `RecordsScene`：从 LifeScene 的“生活记录”入口打开，Q1～Q4 页签在单个 390×844 Canvas 屏幕内展开三个自然月、行动、执行率、资源、人物、兴趣和打断；不使用 DOM 长页，不修改 Core。

季度结果与增龄入口的已查看状态使用独立 `people-life:game-presentation-state:v1` 表现 checkpoint。它只记录已确认的季度 key、年度/年龄入口 key 和当前是执行还是结果阶段，不保存 Phaser 对象、Tween、动画帧或人生事实；删除它最多重播演出，不能改变 Core 结果。事件 pending、事件选择、季度计划、年度确认和四季度事实仍全部由 v5 session 恢复。

## 10. 当前风险与处理

### 风险 A：继续修改旧 DOM 主屏

处理：`public/index.html`、`public/app.mjs`、`public/styles.css` 只允许兼容和缺陷修复；正式主玩法进入新 Phaser 目录。

处理：P1 以行动持续留痕、单一季度推进、人物/资源反馈和真实转场验收，不接受把旧卡片原样搬入 Canvas。

### 风险 C：把模拟规则写进 Scene

处理：GameGateway 是唯一事实入口；Scene 只提交稳定命令并消费 snapshot/cue。

### 风险 D：一次迁移整个人生导致失控

处理：只先迁移 6 岁 Q1，再扩 Q2～Q4；P2 通过前不扩 18 岁。

### 风险 E：旧工作区改动被覆盖

处理：使用独立新目录、精确 `apply_patch`、唯一文件所有权；禁止重置、批量覆盖或删除未审计文件。

### 风险 F：H5 被误解为网页产品

处理：H5 只作为发布容器。正式试玩通过 Chrome 应用模式或 TapTap 测试环境显示全屏 Canvas 游戏，不交付滚动网页。

### 风险 G：旧文档或旧代码把新代理带回错误方向

处理：总纲是唯一产品基线，本文是唯一进度基线。已删除旧方向文档不得通过 Git 历史恢复成正式参考；`public/light-scene/` 和旧 DOM 只能用于审计/回归。新代理必须先读第 0、3、7、8、11 节，不能从文件数量或旧截图推断产品方向。

### 风险 H：自动坐标点击通过，但真人按钮仍不好用

处理：F1 已统一输入反馈并增加鼠标/触摸和辅助 Scene 往返证据；最终仍由产品负责人在可见 Chrome 手动确认。自动通过只记录“功能证据通过”，不能自动关闭人工问题。

### 风险 I：跳过当前界面，继续扩角色创建或 P3

处理：F2 已经提前进入工作区，但其完成结论已回退。执行第 7.1/8.0 节闸门，先关闭 F1 人工复验和 F2 集成问题；P1/P2 人工体验未通过时不得启动 P3。

### 风险 J：占位素材被误称为最终美术

处理：启动徽记、主菜单字标、院落背景、人物、行动图和程序化音效均标注为 placeholder/runtime-input。只有经过统一美术方向、资产生产、实机接入和产品负责人验收后才可标“正式资产”。

处理：Core 能模拟出生到死亡，不等于正式客户端已完成整个人生。任何阶段都必须分别报告“Core 已有”“Phaser 已接”“自动证据已过”“产品负责人已验收”四种状态，禁止合并成一句“已完成”。

### 立项至 D0：模拟底座形成、三次表现方向纠偏

这部分记录发生在当前总纲 v5.0 生效之前，只用于解释决策来源，不恢复任何旧方案的权威性。

#### 第一时期：先证明“一生可以被确定性模拟”

项目从人生模拟内容和规则起步，先后建立出生家庭、城乡与历史条件、童年、小学、青少年、升学/培训/就业、成年工作、伴侣与子女、住房与资产、健康、退休、死亡和人生复盘。为了避免“点击顺序改变随机结果”，建立种子 RNG、命令回放、存档迁移、调试跳龄和大样本校准。这个阶段产生了今天仍然最有价值的 Core。

当时的错误完成感是：因为浏览器页面能从出生跑到死亡、数据和报告很完整，就误以为产品主体已经接近完成。实际上玩家体验仍是读档案、选文字和看报表。

#### 第二时期：在旧 DOM 上不断“做得更像游戏”

旧客户端逐步增加场景背景、人物立绘、行动卡、底部导航、关系/地图/角色/记录页面、过渡、Toast 和结果动画，也建立了多页截图与浏览器检查。它改善了可读性，却没有改变核心操作：玩家仍在网页中打开模块、读卡片、点按钮、等待文字报告。

产品负责人多次指出“这是网页版文字游戏”“像 PPT”“用户是在玩游戏还是点击网页”。由此确认问题不是颜色、阴影、背景图数量或某个按钮位置，而是主玩法的信息架构和交互模型错误。

#### 第三时期：把“不是网页”错误理解为“必须移动与找热点”

项目随后提出场景化重置：让 6 岁角色在 1984 院落中走近伙伴、石桌、自行车和家门，通过热点/物件执行弹珠、识字、看自行车和摆碗等行为。技术上完成过 DOM/Phaser 双 Spike、评分、场景协议、三舞台灰盒、浏览器矩阵和盲测工具。

这个方向虽然认识到人物、物件、动作和即时反馈的重要性，却把人生模拟器变成了固定舞台中的节点移动/热点互动。产品负责人明确追问“为什么一直移动”，并以《中国式人生》说明真正想要的是模块化人生操作、人物与资源持续可见、行动立即反馈和时间推进，而不是移动探索。因此轻场景路线被整体归档。

#### D0 前最终方向确认

产品负责人最终明确：

- 技术架构不能继续鼓励网页卡片主玩法；
- 但改成游戏也不等于制作角色移动、地图、热点或 3D；
- 要做的是一款可以发布的人生模拟游戏，浏览器只用于运行和 Chrome 验收；
- 参考《中国式人生》的游玩方式，不照抄产品；
- 以后开发完成后要能在 Chrome 看 UI、在 H5/目标平台发布，但主屏必须是游戏运行时；
- 方向写入规范，旧错误表述删除，开发进度集中到一份台账；
- 全面开发再次不满意后，改成“一个界面一个界面来做”。

为防止旧方向被误恢复，下列文件已从工作区正式文档中删除：`MVP_DESIGN.md`、`ANNUAL_TURN_SYSTEM.md`、`FULL_GAME_REBUILD_V2.md`、`GAMEPLAY_REBUILD_V3_PROPOSAL.md`、`GAME_DIRECTION_RESET_DECISION.md`、`whole-game-ui-rebuild-plan.md`、`life-stage-visual-architecture.md`、全部 `LIGHT_SCENE_*` 阶段/验收/盲测文档及根目录旧 `design-qa.md`。它们的文件名仅作为“方向墓碑”记录，不是新任务可引用的规格。

   - 抓周界面的开启一生按钮此前也使用了 `p2Button`，存在同样的点击错位隐患。
